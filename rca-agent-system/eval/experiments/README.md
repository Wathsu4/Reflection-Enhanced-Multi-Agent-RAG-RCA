# Evaluation experiments

This directory holds the **ablation, baseline, and extended-metric**
outputs for the thesis evaluation chapter. It is kept separate from the
demo-ready reports in `../` (`results-*.md`, `memory-evolution-*.md`) so
that running experiments never clobbers the numbers used in the live
demo.

Everything here is generated by the existing eval scripts in
`../../scripts/`, driven by a `--ablation` flag. See
`How-To-Evaluate/PLAN.md` for the full experiment catalogue and
priorities.

These same experiments are **browsable and re-runnable from the
frontend's Evaluation tab** (`/evaluation`). The backend registry at
`../../rca_system/eval_api/registry.py` is the single source of truth for
each experiment's metadata (title, plain + technical description, RQ tags,
command, params). Runs triggered from the UI execute as **sandboxed
subprocesses** — each gets its own freshly-seeded ChromaDB under
`../../data/eval-runs/<job-id>/`, so the live/demo knowledge base is never
mutated. Job state is mirrored under `.jobs/` here.

## What lives here

- `results-{ablation}-{timestamp}.{md,json}` — per-variant pipeline
  accuracy + latency + token + retrieval-IR reports from
  `scripts/evaluate.py --ablation <variant>`.
- `memory-evolution-{ablation}-{timestamp}.md` — per-variant score-drift
  reports from `scripts/evaluate_memory_evolution.py --ablation <variant>`.

## Pipeline variants (`--ablation`)

Defined in `rca_system/ablations.py`. All are prompt/wiring changes only
— no re-training, no model swap.

| Variant | Pipeline | Defends / isolates | PLAN id |
|---|---|---|---|
| `none` | retrieval → reasoning → reflection → memory_update (full system) | — | — |
| `reflection_off` | retrieval → reasoning → memory_update | reflection's contribution | E1.1 |
| `memory_frozen` | full pipeline, but score writes suppressed | the score-mutation mechanism vs just having an extra agent | E1.2 |
| `no_rag` | reasoning → memory_update (no retrieval) | value of RAG over pure LLM reasoning | E1.4 |
| `cot_only` | identical to `no_rag`, framed as a baseline | "is the LLM good enough without retrieval?" | E2.2 |
| `retrieval_only` | deterministic top-k, **no LLM** | zero-hallucination floor any variant must beat | E2.1 |

`retrieval_only` performs no Gemini call, so it is rejected by the
memory-evolution script (it never mutates memory).

## How to regenerate

From `rca-agent-system/`:

```bash
# One pipeline-accuracy report per variant (writes here).
for v in reflection_off memory_frozen no_rag cot_only retrieval_only; do
  uv run python scripts/evaluate.py --ablation "$v"
done
# Full system (writes to ../, the demo-ready location):
uv run python scripts/evaluate.py

# Memory-evolution contrasts:
uv run python scripts/evaluate_memory_evolution.py --ablation reflection_off
uv run python scripts/evaluate_memory_evolution.py --ablation memory_frozen

# Smoke-test any variant cheaply first:
uv run python scripts/evaluate.py --ablation no_rag --limit 2
```

## Metrics added for the experiments

Beyond the original keyword/LLM-judge/latency/recall columns, the reports
now include:

- **Retrieval IR triad** (E4.4): Recall@k, MRR, nDCG@k over the in-domain
  scenarios (single relevant incident per scenario → binary relevance).
- **Per-stage latency** (E6.1): wall-clock per agent author.
- **Token usage** (E6.2): mean Gemini tokens per scenario + per-stage
  token counts (from each ADK event's `usage_metadata`).
- **Expected-incident rank**: 1-based rank of the ground-truth incident
  in the retrieval list, per scenario.
